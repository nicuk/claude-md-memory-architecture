# Templates

Copy, then delete every line that doesn't apply. A template line left in "just in case"
is noise that every future session pays to read.

## Contents
- Global `~/.claude/CLAUDE.md`
- Root `CLAUDE.md` / `AGENTS.md`
- Folder `CLAUDE.md`
- Path-scoped rule `.claude/rules/<name>.md`
- `MEMORY.md` index
- Memory topic file (feedback, project, reference, router)
- Registry doc
- Document frontmatter
- `.gitignore` for private-but-tracked decisions

---

## Global `~/.claude/CLAUDE.md`

```markdown
# Global preferences (every session, every repo)

Only what is true in a repo I haven't created yet. Project facts go in that repo's CLAUDE.md.

- <communication preference, e.g. "lead with the answer, then the evidence">
- <working preference, e.g. "commit only when asked">
- <one-line principle, e.g. "log swallowed errors; never let a failed query become 0">
- For detail on <topic>: @~/.claude/<TOPIC>.md
```

Test each line: does it name a stack, a path, a command or a project? Then it belongs in
a project file. Is it a task ("move X", "set up Y")? Then do it now or put it in a
tracker, not here.

## Root `CLAUDE.md` / `AGENTS.md`

```markdown
---
authority: binding
status: live
---

# <Project> — <one-line what it is>

This file holds rules that change a decision. How-to lives in `docs/COMMANDS.md`,
why in `docs/adr/`, and what the code does in the code.

## Where things are
| document | role |
|---|---|
| `docs/adr/` | decisions, immutable (annotate, never rewrite) |
| `docs/reference/<registry>.md` | <kind of evidence>; read before researching <topic> |
| `docs/COMMANDS.md` | how to run, test, deploy |

## Method — how decisions get made here
1. Locate the failure before proposing the fix: name the layer, the metric and its current value.
2. Check `docs/adr/` and the registries before re-investigating anything.
3. <project-specific method rule, with a one-line worked example>

## Hard rules
- <invariant> — <why, in one clause>. Enforced by `<test or check path>`.
- <invariant with no enforcer yet> — (not enforced; stated as intent)

## Verify
The narrowest command that proves each claim above: `<command>`.
```

Keep it under about 300 lines. Before adding a paragraph, ask whether it forbids,
requires or disambiguates something. If it doesn't, it belongs somewhere else.

## Folder `CLAUDE.md`

Only when the subtree has an invariant that the code can't show.

```markdown
# <dir>/ — local rules

- Frozen since <YYYY-MM-DD>: <reason>. New work goes in `<other dir>/`.
- Owned by <team/service>; changes need <what>.
- Never import from `<path>` here: <why>.
- Files here are generated by `<script>`; edit the generator, not the output.
```

Under about 60 lines, and usually under 10. Leave out file-by-file descriptions.

## Path-scoped rule `.claude/rules/<name>.md`

Prefer this over a folder file when the scope is a glob rather than a single directory.

```markdown
---
paths:
  - "**/migrations/**"
  - "supabase/functions/**"
---

- Migrations are append-only; never edit an applied one. Add a new one.
- Confirm a migration is applied with `<narrowest command>`, never a push-all.
```

A rule with no `paths:` loads every session, so it should be in the root file instead.
A glob that matches nothing never loads, and the audit script reports it as a FAIL.

## `MEMORY.md` index

```markdown
# Memory index

- [Owner priorities](owner-priorities.md) — visuals first; brutal measured scoring
- [Read market registry first](market-evidence-registry.md) — docs/reference/market-evidence.md before any market research
- [Deploy verification needs prod](deploy-verify-prod.md) — local auth is a test instance; sign-in checks only on prod
```

One line each, under about 150 characters: what it is, then when it matters. Order by
how often a session needs it. Budget: 3KB is comfortable. Past 200 lines or 25KB, the
rest is never loaded.

## Memory topic file

```markdown
---
name: <kebab-case-slug>
description: <one line: the fact and when it matters>
metadata:
  type: feedback            # user | feedback | project | reference
---

<The fact or rule, stated once.>

**Why:** <the incident or reason, with an absolute date>.

**How to apply:** <when it triggers, and what to do; the verifying command if there is one>.
Related: [[other-memory]].
```

Variants:
- **project status**: start with "As of YYYY-MM-DD:" and end with "Re-check: `<command>`".
- **reference**: where something lives outside the repo (a dashboard, a thread, a vendor
  doc) and what it is good for.
- **router**: "Read `<repo doc>` before <kind of work>. It already holds <what>. Add new
  findings there in the same commit." Router memories are the highest-value kind.
- **retraction**: put `~~old claim~~ RETRACTED YYYY-MM-DD: <why>` at the top and keep the
  corrected claim below it.

## Registry doc

```markdown
---
authority: reference
status: live
---

# <Kind of evidence> registry

Read this before researching <topic>. Add new findings here in the same commit as the work that used them.

| item | value | source | date | confidence |
|---|---|---|---|---|

## Not yet researched
- <gap> — so nobody assumes it was covered.
```

## Document frontmatter

```yaml
---
authority: binding | decision | brief | reference | postmortem
status: live | historical
superseded_by: docs/adr/ADR-014-x.md   # optional, historical only
---
```

Precedence: binding > decision > brief > reference. A postmortem is evidence, not a rule
source. A dead pointer in a `historical` document is a WARN; in a `live` document it is a
FAIL.

## `.gitignore` for private-but-tracked decisions

```gitignore
# Private working files stay local; decision records keep their history.
# The `/*` form matters: a bare `_internal/` stops git descending, and the
# negation below could never reach inside it.
_internal/*
!_internal/docs/
```

Verify on exact files, not directories:
`git check-ignore -v _internal/scratch.md` (expect a match) and
`git check-ignore -v _internal/docs/ADR-001.md` (expect no match).
